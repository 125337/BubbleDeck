# BubbleDeck 授权系统方案 V1（评审稿）

> 2026-11-03 · 状态：待确认
> 范围：卡密激活 + 服务器验证 + 在线气泡包分发。发卡/支付渠道**不在范围内**（用户自理）。

## 一、架构总览

```
        ┌────────────────────────────────────────────┐
        │                插件端（dylib）               │
        │  激活页 → Keychain 存 token → 在线列表 → 下载 │
        │           → 带 key 解密解压 → packs/         │
        └───────┬────────────────────────┬───────────┘
                │ HTTPS + HMAC 签名       │ HTTPS 下载 .bdpack 容器
        ┌───────▼────────┐      ┌────────▼─────────┐
        │  授权 API（自有服务器）│      │  包存储 = 哑管道   │
        │ activate        │      │ 存储：GitHub Releases │
        │ verify          │      │ （备选：COS 签名URL） │
        │ packs           │      │ 公开可下，无 key   │
        │ download(含key) │      │ 下载了也没用       │
        └────────────────┘      └──────────────────┘
```

- **授权 API**：自有轻量服务器（已有资产）跑单进程 HTTP 服务 + systemd 常驻，域名 + HTTPS
- **包存储**：**GitHub Releases 存 .bdpack**（零注册零成本），公开可下但无 key 打不开——哑管道，URL 泄露≠白嫖。若后续国内下载速度不达标，可平移 COS，客户端只认 API 下发的 URL，换源不改客户端
- **密钥通道**：`.bdpack` 密钥只走授权 API 的 /download 响应下发（验 token 才给），存储层永久公开
- **数据存储**：服务器本地 **SQLite**（license 绑定、token、packs 表含每包密钥）——直接是正式形态，无迁移妥协

## 二、绑定模型

| 项 | 规则 |
|---|---|
| 绑定键 | `license_key ↔ (device_id, wxid)` |
| device_id | IDFV（宿主 App 维度，同一设备稳定） |
| wxid | 当前登录账号，仅作记录展示，**不作校验键**（可改） |
| 卡有效期 | **永久**（用户不付费续期；卡无到期日） |
| 设备数 | 1 卡 = 1 设备 |
| 换绑 | **V1 不做**（换设备 = 重新发卡） |
| 验证节奏 | 插件**每次微信启动/回前台都报到**（verify，封卡≈下次打开微信即失效）；本地凭证 **7 天兜底**（纯断网时最多撑 7 天）；token 过期后插件用卡密自动重新激活（同卡同设备不占名额，用户无感） |
| 系统版本/机型 | 仅上报记录，不参与校验 |
| 历史账号列表 | V1 不做（隐私敏感+需逆向），V2 再议 |

## 三、接口契约

通用约定：

- Base URL：`https://<你的域名>/bd`（用已有域名，部署后定）
- 全部 POST，`Content-Type: application/json`
- 防抓包基础层：请求头带 `X-BD-Ts`（毫秒时间戳）+ `X-BD-Sign = HMAC-SHA256(SALT, ts + "|" + body)`，服务端校验签名和时间窗（±300s）。SALT 内置于 dylib（防小白级别，V1 明确不做强对抗）
- 响应统一格式：`{ "code": 0, "msg": "ok", "data": {...} }`，code=0 成功

### 1. 激活 `POST /activate`

```jsonc
// 请求
{ "license": "XXXX-XXXX-XXXX-XXXX", "device_id": "IDFV", "wxid": "wxid_xxx",
  "sys": "iOS 17.2.1", "model": "iPhone16,1" }
// 成功 data
{ "token": "随机48位", "expires_at": 1730000000 }   // token 有效期 30 天，verify 可续期
// 失败 code
// 1001 卡密不存在  1002 卡密已停用  1003 设备数超限  1004 参数缺失
```

同设备重复激活 = 续 token，不占新设备名额。换机 V1 不支持（重新发卡）。

### 2. 验证 `POST /verify`

```jsonc
// 请求
{ "token": "...", "device_id": "..." }
// 成功 data
{ "active": true, "expires_at": 1730000000 }   // 有效则顺延 token 有效期
// 失败 code：2001 token 无效/过期 → 客户端清 token 回激活页
```

客户端策略：微信启动时静默验一次，结果缓存 24h（离线宽限：24h 内验不了不锁功能，超宽限才回激活页——防止服务器抖动误伤付费用户）。

### 3. 包列表 `POST /packs`

```jsonc
// 请求 { "token": "..." }
// 成功 data
{ "packs": [ { "name": "蜜糖邦尼气泡包", "version": "1.0", "size": 2048000,
               "md5": "...", "url": "https://...(.bdpack 直链)" } ] }
```

### 4. 下载 `POST /download`

```jsonc
// 请求 { "token": "...", "name": "蜜糖邦尼气泡包" }
// 成功 data
{ "url": "https://...", "md5": "...", "key": "该包 .bdpack AES-256 密钥(32字符)" }
// key 只在验过 token 后下发；测试期=GitHub 直链，收费期=COS 限时签名 URL
```

客户端下载 → md5 校验完整性 → **CommonCrypto 解密 .bdpack → 得标准 zip → SSZipArchive 普通解压** → 落盘 `Documents/BubbleDeck/packs/<name>/` → 触发重载。

## 四、包加密机制（从第一天生效）

> 设计参考 ThemePro 逆向结论（自定义容器思路），修正其两个缺陷：密钥不明文进文件头（ThemePro 把 K1 放头部=外层失效）、IV 用随机值不 Fixed-IV 全零（防已知明文块分析）。

**容器格式 `.bdpack`**：

```
偏移 0   │ "BDPK" 魔数（4 字节）          ← 通用工具不识别，文件名/结构全藏
偏移 4   │ 版本号（1 字节，当前 = 1）      ← 未来格式扩展用
偏移 5   │ 随机 IV（16 字节，每次打包随机） ← CBC 教科书用法
偏移 21  │ AES-256-CBC(整个 zip, PKCS7)   ← 密钥 K（32 字符随机，不进文件）
```

| 项 | 规则 |
|---|---|
| 加密方式 | AES-256-CBC + PKCS7（CommonCrypto 教科书用法，零自创密码学） |
| 密钥通道 | 每包一个密钥 K，服务端 packs 表保管，**只在 /download 验 token 后下发**——存储层永久拿不到密钥 |
| 客户端解密 | CommonCrypto（系统自带，~80 行）解出标准 zip → SSZipArchive 普通解压（**无需 vendor minizip 的 AES 分支**） |
| PC 打包 | Python `cryptography` 库加密（现成库），一条命令出 .bdpack + 上传 + 登记 |
| 上传物 | `<包名>-<版本>.bdpack`，md5 记录加密后的文件 |
| 密钥泄露应对 | 轮换：改 K 重新封装 → 重传 Releases/COS → 服务端 packs 表更新 → 版本号 +1。人工流程，一次 10 分钟 |
| 防护边界 | URL 可被抓但无 K 无用，连包内文件名都不可见；K 验 token 才发。**不防买家转发**（K+文件一起给出去就破），见「已知妥协」 |

## 五、卡密设计

- 格式 `XXXX-XXXX-XXXX-XXXX`（大写字母+数字，去易混字符），服务端随机生成
- 状态机：`unused → active → (revoked)`
- 服务端字段：license、state、bind_device、bind_wxid、activated_at、rebind_left、token、token_exp
- 发卡：本地 Python 脚本生成 + 导入（发卡平台对接由你自理，届时只需一个"批量导入"入口）

## 六、任务拆分

| # | 任务 | 产出 |
|---|---|---|
| S1 | 授权 API 服务（四接口 + SQLite + 发卡脚本），部署到轻量服务器 | 一个可 systemd 常驻的服务 + script.py |
| S2 | PC 打包脚本（zip → .bdpack 加密封装/md5/传 Releases） | 一条命令出 .bdpack + 上传 + 登记 |
| C1 | TDNet 网络层（签名/重试/超时） | ~200 行 |
| C2 | 激活页 UI（输卡密/激活状态展示） | ~300 行 |
| C3 | 在线列表页 + 下载进度 + md5 校验 + .bdpack 解密（CommonCrypto ~80 行）+ SSZipArchive 普通解压落盘 | ~650 行（SSZipArchive 普通解压版 vendor） |
| C4 | Keychain token 管理 + 启动静默验证 + 离线宽限 | ~150 行 |
| C5 | 收费闸门：未激活时 hook 空转（取图全放行官方） | ~20 行 |

依赖关系：C1→C2/C3/C4 可并行；S1/S2 与 C1 并行；C5 最后收口。

## 八、已知妥协（V1 明确接受）

1. SALT 内置客户端 → 理论可被 dump，挡小白不挡逆向（V2 按真实破解事件加固）
2. SQLite 单文件库在轻量服务器本地，量级（<1 万用户）毫无压力，备份=拷文件
3. GitHub 直链国内不稳 → 测试期可忍，收费期必切 COS
4. **key 交付即尽**：付费买家拿到 key+zip 可转卖/群共享，加密防"外人抓 URL"不防"买家本人分享"。应对靠轮换（发现泄露换密码）+ 授权绑定收口设备数；彻底方案是流式解密（key 不落盘、按块解密）V2 再议
5. `.bdpack` 为自研轻容器，只加密不签名——完整性靠 md5（下载后已校验）；格式扩展靠头部版本号字段（已预留），V2 如需抗篡改可加 HMAC 尾部
